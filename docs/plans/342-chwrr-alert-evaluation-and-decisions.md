# Plan 342 — complete alert evaluations and CHWRR warning decisions

## Status and scope

**DRAFT — not implementable.** This plan takes the alert-evaluation and warning-decision work out of the former combined Plan 340. It depends on Plan 340's as-used forecast evidence and Plan 341's human principal, selected forecast publication and durable publication event. It does not send email/Slack, generate CAP, edit thresholds/models/QC rules, implement a bulletin, or build `sapphire-flow-map`. Operational warning behavior, storage and API authorization make it high-risk under `docs/workflow.md`.

The existing `alerts` table is a mutable active projection with `raised | acknowledged | resolved`; repeated triggers can replace detection or acknowledgement fields (`store/alert_store.py`). The existing `POST /api/v1/alerts/{id}/acknowledge` returns 501. Those states are not a hydrologist's publication judgment. New evaluation and decision history must be keyed to a specific cycle and kept separately.

## Locked behavior

1. **Account for every expected check.** Before checking, persist an immutable manifest of expected station/parameter/level/cycle/source/strategy keys. For `published_forecast`, include the immutable Plan 341 publication decision ID in the expectation and terminal-result uniqueness key: same-cycle A→B→A decisions each require their own result, while redelivery of one decision event must not duplicate it. Append each execution attempt and its failure cause; a separate mutable progress projection may show `not_evaluated` until one immutable terminal result per key is committed: trigger, no trigger, or skipped/unavailable with reason. A failed attempt is never a terminal correct negative; retry appends another attempt and may produce the one terminal result without rewriting failure history or duplicating the key. A permanently unavailable input may be closed as terminal skipped/unavailable with a reason and retains prior attempts. Missing checker invocation becomes `not_evaluated` plus a failure signal, never an absent row. Include source (`raw_forecast`, `published_forecast`, `observation`), stable cycle or observation identity, threshold direction/value and as-used alert strategy/probability configuration. For an observation check, copy the exact evaluated value, timestamp, unit, QC status/flags and source or observation-revision identity into the immutable result; a later rating-curve or QC correction must not rewrite what the checker saw. The mutable `alerts` projection cannot rewrite evaluation history. Pipeline-health alerts remain internal.
2. **Check high and low flow.** Evaluate configured ABOVE and BELOW danger levels for discharge/water level using directional comparison. The current forecast checker skips BELOW and the observation checker compares only `>=`. Preserve source and level; a threshold crossing does not alone establish impact severity (WMO-1150 in `docs/standards/wmo.md`).
3. **Recheck the selected publication.** Consume Plan 341's idempotent publication, same-key replacement and withdrawal events. A replacement event names both the former and newly selected forecast/publication decision IDs; it is a new selected-forecast check, not a withdrawal of the older publication's historical record. Under `threshold_check_mode=published|both`, apply existing `AlertEligibility.SKILL_FORECAST`, minimum ensemble and forecast-output QC rules before checking stored selected-forecast values against as-used thresholds. An ineligible fallback or QC-rejected forecast yields `skipped_ineligible_model` or `skipped_qc_failed`, never a warning candidate. Persist source forecast ID and publication decision ID. Keep raw pooled/primary and selected-forecast results as distinct cohorts; show disagreement to the hydrologist. `raw` remains an internal early-warning mode, not authorization for external release. Reject activation of CHWRR forecast-backed warning publication under `threshold_check_mode=raw`; explicit observation-only warning operation may use that setting only with forecast-backed warning publication disabled.
4. **A human decides on each triggered candidate.** Publication states are `PENDING -> PUBLISHED`, `PENDING -> DISMISSED`, or `PENDING -> EXPIRED` at its fixed deadline; PUBLISHED may become `WITHDRAWN`, become historical `REPLACED`, or become `EXPIRED` at the recorded `valid_through`. Each transition records verified actor, UTC time, controlled reason and optional note in append-only history, atomically with a mutable current-state projection. A dismissal affects only that evaluation: a later continuing or worsening cycle creates a new PENDING candidate; a higher level appears separately. In T2, link each immutable terminal evaluation to an incident through a separate append-only evaluation-to-incident association keyed by evaluation ID; never update the T1 result. Resolve an incident under a persistent scope lock keyed uniquely by `(tenant, station_id, parameter, direction)`: a triggered candidate reuses that scope's open incident ID; create a new incident only when the prior one is closed. Close an incident only when it has neither a current warning nor a live PENDING candidate and terminal no-trigger/clear results for all enabled source cohorts follow its last trigger. Keep the scope projection and version even after closure; it stores the open incident ID and current warning pointer. The database-enforced scope key permits at most one current warning across incident IDs, so a new incident cannot bypass replacement. Publishing a new candidate while that projection names another warning requires an explicit `replace` action naming the prior publication ID and expected warning version (the current-warning projection version), with controlled `superseded` reason and optional note. Lock that scope projection and append the old warning's `REPLACED` transition, new candidate's `PUBLISHED` transition, audit records and pointer/version change in one transaction; stale ID/version returns `409` with no change. The old warning stays in history but disappears from ordinary current-warning reads. Clear, lower-level or dismissed new candidates flag a still-current warning for duty-hydrologist review; they never replace it automatically. At the first immutable triggered evaluation, snapshot CHWRR-managed `warning_validity_hours` (proposed default 24) and fix the candidate's `valid_through`: for a forecast, the earlier of evaluation time plus that duration and the last triggering forecast valid time; for an observation, the as-used observation timestamp plus that duration. Publication copies this deadline; its click time never restarts or extends validity. Later configuration changes affect new evaluations only and do not rewrite existing candidates or publications. A station-scoped duty hydrologist may replace or withdraw when the original publisher is off duty. No automatic release or escalation bypasses review.
5. **Keep reasons distinct from later outcomes.** Dismissal codes include `model_unlikely`, `data_quality`, `threshold_not_relevant`, `recipient_not_relevant`, `duplicate`, `superseded`, `other`; `other` and every withdrawal require a note. Plan 343 later classifies `correct_dismissal`, `wrong_dismissal`, `true_but_not_relevant` or `indeterminate` using observations and CHWRR relevance judgment. Preserve both records.
6. **Gate all warning outlets.** CHWRR consumer and Plan 401 reviewer tokens on ordinary `GET /api/v1/alerts` and detail return the same active, human-PUBLISHED warning evaluations for the same station scope and validity window; never PENDING, DISMISSED, pipeline-health or raw candidates. Keep raw/pipeline inspection on a named-human review route or a separately authorized internal operations route. Use stable evaluation/publication IDs instead of mutable alert UUIDs. New cycles do not auto-publish updates, and ordinary consumer/reviewer payloads cannot expose unpublished forecast values. Plan 110 webhook and Plan 266 CAP must consume this human-publication ledger, including approved observation warnings and audited replacement/withdrawal, never the mutable `alerts` table. Both external hydrological outlets remain disabled for the CHWRR MVP; pipeline-health operations alerts remain separate.
7. **Keep linked publications consistent.** Forecast-backed warning publication requires a triggered `published_forecast` recheck linked to a still-active selected forecast publication. Reject `raw_forecast`, skipped, nontriggered or stale-source candidates inside the publish transaction. A delayed recheck cannot release a warning after all triggering forecast valid times have passed, at or after the candidate's fixed `valid_through`, or after its source publication was replaced/withdrawn; test this under backlog catch-up. An observation-backed candidate is likewise blocked at or after its fixed observation-time deadline and has its separate human approval path. At every warning publish/replacement transaction, check Plan 341's trusted current backup-health gate and the linked forecast's proof deadline: an in-window `backup_pending` source is allowed as the owner decided, but an overdue proof or unhealthy global backup blocks *new* warning release. Existing released warnings remain visible and authorized withdrawal remains possible during a backup outage. A selected forecast with a current linked warning cannot be withdrawn **or replaced at the same station/parameter/issue key** without a joint authorized transaction. For replacement, the hydrologist is shown that the old warning will be withdrawn; the Plan 341 request names the warning publication ID, expected version, explicit `withdraw` action and reason. One transaction publishes the new selected forecast, withdraws the old linked warning with reason and audit history, and emits the replacement/recheck event. The new forecast's warning candidate is checked afterward and remains PENDING until a separate human decision; no warning is silently carried over or auto-published. If the duty hydrologist does not authorize that joint action, or the warning version changed, reject the forecast replacement with no state change. A later outbox event cannot repair this invariant. Publishing a newer issue time leaves the earlier issue's warning to its separately recorded validity and warning-replacement rules.
8. **Enforce append-only history in the database.** Expectation manifests, execution attempts, immutable terminal evaluation results and warning decision transitions reject `UPDATE`, `DELETE` and `TRUNCATE` under role-independent migration guards; grant INSERT only to the appropriate service role. A mutable current-state/processing projection uses separately scoped privileges. Exercise guards as API, worker and privileged non-owner roles. Keep evidence, attempts, evaluations and decision rows outside cleanup until Plan 344 proves linked archival; use Plan 340's protected backup and six-year retention floor. Extend the clean-volume restore rehearsal beyond Plan 340's single forecast sample to a linked forecast publication → threshold expectation/attempt/result → warning decision/history chain, with content checks and a missing/corrupt-ledger failure case before CHWRR warning release is enabled.

Dashboard contract: bounded, scoped, paginated `GET /api/v1/review/alert-candidates` and detail for a named CHWRR human with a local station `review` grant; consumer, reviewer and admin service tokens are denied. Every `POST .../{id}/publish`, `/dismiss`, `/withdraw` requires that same named human to hold a current station-scoped `publish` grant from Plan 341; a review-only hydrologist can inspect candidates but cannot decide them. Each POST uses expected version and idempotency key; dismissal/withdrawal also require reason code/note, and replacement supplies the prior warning ID and expected warning version specified above. Authorize against the current grant before idempotency replay. Scope the key to actor, tenant and route; an exact replay returns its committed decision even after later state changes, but a changed payload returns `409` and another actor or revoked grant cannot retrieve it. Plan 401's server-side dashboard token remains GET-only and can read ordinary published warnings and Plan 402 diagnostics, but cannot inspect pending candidates or authorize a decision. Ordinary `GET /api/v1/alerts` and detail expose only current published warnings to same-scope consumer/reviewer tokens. Replace or explicitly retire the acknowledgement stub; never repurpose it as dismissal. Define exact status codes and schemas in `docs/spec/types-and-protocols.md` during implementation. The separate MVP dashboard may demo candidate evidence, pending state, decision reasons and later outcomes through the human review path; local mocks must be labelled illustrative until the backend exists.

### T2 — Human warning decision ledger and API

**In / Out.** In: decision types/store, incident lineage and scope-unique current-warning projection, API routes/schemas, audit events, DB/API grants, cache behavior and scope checks. Under the scope lock, assign each terminal evaluation to an incident in an append-only association, including no-trigger results used for closure; duplicate processing cannot add a conflicting association. Apply the closure rule above without mutating T1 results. The publish transaction rejects `raw_forecast` candidates and any `published_forecast` evaluation that is not triggered, has no future triggering valid time, reached its fixed `valid_through`, or has an inactive source selection; check under the same transaction/lock as the decision. Observation candidates retain their own human approval path and fixed observation-time expiry. Use T1's snapshotted warning-validity setting and fixed candidate `valid_through`; copy that deadline to any publication without resetting it. Reject stale versions, invalid transitions, cross-station actions, and idempotency-key reuse with a different payload. Expiry, replacement and withdrawal retain history. Reconcile due PENDING candidates and published-warning expiries in T1's restartable scheduled worker with an attributable system actor; expired PENDING candidates are non-actionable and no longer live for incident closure. ordinary GET filters at `valid_through` even if the worker is late. Before any decision or linked forecast withdrawal, reconcile an overdue expiry under the same scope lock so a stale pointer cannot block or replace an expired warning. Append the `EXPIRED` transition, clear the pointer and increment its version atomically; never delete the old publication. Implement or reject both linked forecast/warning withdrawal and same-key selected-forecast replacement atomically; the latter requires Plan 341's typed warning ID/version/action/reason and withdraws the old linked warning before an asynchronous recheck can produce a new PENDING candidate. Check trusted backup health and the linked source's proof deadline at every new warning publish/replacement; permit in-window `backup_pending`, block overdue/unhealthy, but still allow authorized withdrawal. Extend the protected restore rehearsal to the linked publication/evaluation/decision chain. Do not enable CHWRR warning consumer mode before Plan 340's protected backup/restore and this plan's no-cleanup guards are proven. Out: automatic delivery, CAP, bulletin release, general acknowledgement/assignment workflow.
