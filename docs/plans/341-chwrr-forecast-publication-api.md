# Plan 341 — CHWRR forecast review and publication API

## Status and scope

**READY for implementation — CHWRR publication remains disabled.** The orchestrator set READY after the independent high-risk reviews and Plan 340's status reconciliation merged in PR #317. T1 (human identity, #322), T2 (publication ledger, #325), and T2b (per-publication protected proof, #327) are on main as of `e6e7c444`; T3 and T4 remain. Plan 340 T1/T2/T3 software is on main; its remaining DHM protected-target and Nepal-sized restore proof is an activation gate, not a blocker to implementing T3 against a test identity provider. Security, human authorization and external API behavior make T3 high-risk under [retired workflow](https://github.com/hydrosolutions/SAPPHIRE_flow/blob/0dbe7217f1f7241a40d4ba5a9b5ef4a750fbc169/docs/workflow.md). Do not enable CHWRR publish writes or published-only consumer mode until this plan's exit gates and the Plan 340/342 activation prerequisites pass.

This is backend support for the separately built `sapphire-flow-map` dashboard. It follows Plan 340's first-run evidence capture and covers forecast review, one-forecast publication, withdrawal, and authenticated consumer reads. It does not build the dashboard, bulletin artifacts, warning publication (Plan 342), CAP (Plan 266), email/Slack delivery (Plan 110), or model editing. `docs/v0-scope.md` intentionally deferred Flow 3; this is a CHWRR follow-on, not a claim that v0 already shipped review.

## Existing boundary and decisions

- `ForecastStatus` has `raw | reviewed | published | superseded`. Plan 328's automatic retry may change an existing row to `superseded` and insert a new RAW forecast for the same natural key; it retains the old values and evidence. `PgForecastStore.transition_status` changes forecast status in place with optimistic versioning but has no API caller or publication audit event. The existing status column cannot be the authority for CHWRR publication: an automatic retry could otherwise silently remove a human-approved forecast from consumer reads. `audit_log` and `AuditEventType.FORECAST_STATUS_CHANGE` exist (`types/enums.py`, `store/forecast_store.py`, `db/metadata.py`).
- Current authenticated `GET /api/v1/forecasts/{id}`, station forecast list, and forecast-lab snapshot can expose raw forecasts (`api/routes/api_forecasts.py`, `api_stations.py`, `forecast_lab.py`). A publication gate must cover all consumer-facing forecast paths, including legacy JSON and caches/exports.
- Service access tokens now include GET-only consumer, reviewer and admin identities (Plan 401, #320; `api/security.py`). The reviewer token remains scoped like a consumer on ordinary routes and cannot identify the approving hydrologist. T1's `api/human_auth.py`, `store/human_identity_store.py`, local user UUID, external `(issuer, sub)` link and station grants (#322) provide the named human boundary; T3 must use it for candidate review and decisions. Local password/TOTP login remains deferred.
- Activate published-only reads per CHWRR tenant after the review/write path, Plan 342's warning recheck and Plan 340's protected evidence backup/restore are ready. Preserve existing Swiss/internal diagnostic access to RAW forecasts in a separately authorized internal route; do not change every service-token route globally while this tenant-specific workflow is being introduced. Explicitly classify each existing API/legacy JSON/forecast-lab/export route as consumer or internal diagnostic and test the applicable principals. Plan 402's `GET /api/v1/qc/rules` and `GET /api/v1/stations/{id}/skill` are REVIEW-class internal diagnostics with no forecast values, so the publication gate does not filter their responses. Plan 401's reviewer token may read those diagnostics, but it sees only published values on ordinary forecast routes and cannot read this plan's unpublished candidates. The dashboard uses the named hydrologist's OIDC principal for candidate review and decisions.
- Rollback after activation is a security operation as well as a schema operation: a pre-gate API image would expose RAW forecasts through its old reads. The production Compose base publishes Caddy's ports but no API host port. Before starting a pre-gate image or restoring an old database, disable the `sapphire-flow.service` boot unit described in `docs/standards/cicd.md` (without invoking its `ExecStop`, which runs `compose down`), stop Caddy, and verify from outside the host that `/api/v1/*` and legacy forecast pages cannot be reached; stop if any direct API port or alternate ingress remains. Keep boot auto-start inhibited and Caddy stopped through the old-image interval. Restore ingress and the boot unit only after a gate-capable image and its activation checks are back. This intentionally interrupts every external API consumer during rollback. Do not run an unscoped Compose `up` that restarts Caddy while the old image serves RAW. T3 proves the isolation mechanics with its disabled build; Plan 342 owns the later activated rollback/recovery rehearsal, including a reboot or equivalent boot-unit check on the DHM target before activation.
- **One click selects one immutable forecast ID for publication.** Keep CHWRR publication in an additive, append-only decision ledger and a transactionally updated current-selection projection, separate from `forecasts.status`. Do not add `ForecastStatus.WITHDRAWN` or use the forecast status column as the publication flag. `REVIEWED` remains reserved for later multi-step review. At most one forecast is currently selected for each `(tenant, station_id, parameter, issued_at)`, independent of model. The projection has a persistent row and monotonically increasing version for each key: withdrawal clears `selected_forecast_id` but does not delete the row or reset its version. A null expected version means the key has *never existed*, not merely that it is currently empty. Enforce in the database that any selected forecast ID belongs to that exact tenant/station/parameter/issue time; a unique key alone cannot prevent a mismatched or cross-tenant pointer. The decision ledger retains every previously published ID. A rejected/unselected forecast has no publication decision, whatever its generation status. The dashboard derives publication badges from this ledger, not from `ForecastStatus`.
- **Automatic retry never publishes or retracts.** Plan 328 may mark a forecast `superseded` and create a replacement RAW row. If the old ID was selected for publication, it stays selected and readable with its original values until an authorized hydrologist publishes a replacement or explicitly withdraws it. The new row is an unpublished candidate. Consumer authorization and `latest-published` queries use the publication selection, not the current-forecast filter that excludes `superseded` rows. This preserves the last human-approved answer while the replacement awaits review.
- **Evidence at the publish boundary.** Never publish a pre-0057 forecast with no Plan 340 evidence row: its values are outside the evidence-linked no-cleanup guard. Require the captured manifest, input snapshot, output values and references needed to diagnose that exact forecast, with no missing-material cause other than the pending protected-backup/image-byte proof. Review list/detail shows immutable `capture_status`, derived `effective_preservation_status`, attestation ID, remaining reasons and whether this forecast's backup proof is pending. A hydrologist may publish while *that forecast's* next protected restore proof is pending, as the owner decided for alert-day timeliness, only if Plan 340's protected target, no-cleanup policy and fresh successful backup/restore health gate are active. Store `preservation_at_publish = verified | backup_pending` on the immutable publication decision and show it in the response; schedule/reconcile the forecast-specific proof and raise an operations health alert if it is still missing after the configured freshness window (initially 36 hours). An overdue pending proof blocks further CHWRR publish writes until resolved but never silently withdraws an earlier human publication. Missing evidence, another unresolved capture gap, a stale/unhealthy protected backup or an unconfigured target blocks new publication or replacement. An authorized, reasoned withdrawal of a current or historical forecast remains possible during a backup outage, including a joint linked-warning withdrawal under Plan 342. The API must read a trusted, freshness-bounded backup-health projection written by the host backup process with restricted privileges; it cannot inspect the host-only volume or accept a caller-supplied health flag. The Mac mini has no separate protected volume, so real publication remains disabled there.
- **Routine replacement is a new publish decision, not a withdrawal.** A hydrologist may publish a newer issue time or replace the selected forecast for the *same* station/parameter/issue time. For the same key, one transaction appends the new publication decision, moves the current-selection pointer, records the replaced publication decision and forecast IDs plus actor/time, and emits a change-feed event carrying both IDs. The older publication and its values remain available in historical reads and audit history, with a derived `replaced` label; no withdrawal reason is requested. For a newer issue time, the earlier issue remains selected for its own key and historical queries; `latest-published` moves by issue time. A previously replaced forecast may be selected again only through a new attributable publish decision if it is still an eligible, non-`superseded` candidate; history is keyed by immutable decision ID so an A→B→A sequence remains unambiguous. A withdrawn forecast ID cannot be re-published. After authenticating and checking the caller's *current* station grant, an exact idempotency-key replay scoped to that actor/tenant/route returns its committed decision before current candidate/selection checks, even if a later retry superseded the forecast or another publication replaced it; reusing the key with different input remains `409`.
- Publishing a forecast is a new threshold-check input. Emit a durable, idempotent publication or replacement event in the same transaction as the decision, containing the selected forecast ID, immutable output/version, actor and replaced ID when applicable. Plan 342 consumes it to evaluate the *selected* forecast under `threshold_check_mode=published|both`, even if the raw candidate came from a different model or pooled strategy. The CHWRR consumer publication mode must not be activated until that recheck and its human warning review path work; `raw` remains an internal early-warning path. Withdrawal emits a separate event for warning reconciliation. Document the intentional one-click selection simplification against Flow 3 in `docs/architecture-context.md`.
- **Withdrawal means reasoned retraction, not routine replacement.** An authorized hydrologist may retract a currently selected *or historical replaced* forecast ID found erroneous. It requires a reason and preserves the forecast and all publication decisions. If that ID is the current selection, withdrawal clears the pointer and increments its version; if it was already replaced, the newer current selection stays intact. Withdrawal tombstones every consumer-visible publication of that forecast ID and emits an invalidation event, while an authorized CHWRR audit view retains the full record. A later different forecast for the same key may be published. No in-place correction or re-publication of the withdrawn ID.
- Do not permit withdrawal **or same-key replacement** of a selected forecast with a current linked warning until Plan 342 supplies a joint forecast/warning decision transaction. A later outbox event cannot enforce this invariant. Before that transaction exists, reject either action without changing the selection or warning. After it exists, require an explicit typed `linked_warning_withdrawal` action naming the current warning publication ID, expected warning version and reason; the dashboard explains that the old warning will be withdrawn and obtains the hydrologist's consent. One authorized action must commit the forecast publication change, warning withdrawal and both audit records together or none; a missing/stale warning action returns `409`. A historical replaced ID is not linked to a current warning under Plan 342's active-selection invariant; detect and reject any inconsistent legacy link rather than silently tombstoning it. Publishing a newer issue time does not silently retract the earlier issue's linked warning; Plan 342 decides its separate validity/replacement lifecycle.
- Consumer endpoints remain authenticated. `latest-published` returns the selected forecast from the newest published issue time per station/parameter, with a deterministic tie breaker. The ordinary consumer list returns one current selection per issue time. Historical list/detail retains *all* publication decisions, including replaced and `superseded` forecast rows with full original values; if an ID was later withdrawn, every occurrence becomes a metadata tombstone. An authorized CHWRR audit view includes full withdrawn records and their decision history. No public unauthenticated path in this slice.

## API contract for the dashboard and consumers

| Principal | Route | Behavior |
|---|---|---|
| Verified CHWRR human with a local station review grant | `GET /api/v1/review/forecasts?station_id=...&start=...&end=...` and `GET /api/v1/review/forecasts/{id}` | Scoped candidates with model, quality, forecast version, generation status, separate publication state and selection version, plus Plan 340 capture/preservation status, attestation ID, remaining reasons and backup-pending state; pagination and bounded date range. Consumer, reviewer and admin service tokens are denied. |
| Same, with publish permission on station | `POST /api/v1/review/forecasts/{id}/publish` | Body contains `expected_forecast_version`, `expected_selection_version` (null only when the key has never existed), and an idempotency key. Lock and recheck the candidate forecast inside the publication transaction against Plan 328's supersession writer; a stale or `superseded` candidate, changed selection, or stale first-publish request returns `409`. Exact-key replay returns the original result before those checks. A same-key replacement names the former selected ID and needs no *forecast* withdrawal reason; if a current warning is linked, additionally require `linked_warning_withdrawal: {action: "withdraw", warning_publication_id, expected_warning_version, reason}` with explicit hydrologist consent, or reject. |
| Same, with publish permission on station | `POST /api/v1/review/forecasts/{id}/withdraw` | The ID may be the current selection or a historical replaced publication. Body contains `expected_selection_version`, idempotency key, and required forecast-retraction reason. If the selected ID has a current linked warning, additionally require the typed `linked_warning_withdrawal` action above after Plan 342's joint transaction is active; otherwise reject. Only withdrawing the selected ID clears the pointer. Automatic forecast-version changes do not themselves authorize or prevent withdrawal. |
| Existing service consumer, reviewer or admin token | `GET /api/v1/stations/{id}/forecasts`, `GET /api/v1/forecasts/{id}`, `GET /api/v1/stations/{id}/forecasts/latest-published` | CHWRR publication gate applies to all three roles; consumer and reviewer station scope is identical, while admin retains its existing unscoped read role per `docs/standards/security.md`. List/latest use current publication selections, even if their source forecast row is `superseded`. By-ID detail serves both current and replaced published IDs with original values; an unpublished ID returns 404 and a withdrawn ID returns 410 with metadata-only tombstone. `GET` remains read-only. |
| Same read principals | `GET /api/v1/stations/{id}/forecast-publications?cursor=...&limit=...` | Bounded historical publication decisions keyed by decision ID, including current and replaced IDs with their original values and withdrawn metadata tombstones, independent of generation status. Reviewer and same-scope consumer get identical CHWRR values. |
| Same read principals | `GET /api/v1/forecast-publications?cursor=...&limit=...` | Bounded, station-scoped publication, replacement and withdrawal change feed for downstream cache invalidation; replacement names the former and new selected IDs, without exposing unpublished forecast values. Reviewer and same-scope consumer get identical CHWRR events. Return a stable next cursor. |

Response schema exposes stable forecast and publication-decision IDs, station, parameter, issue/valid times, model/artifact identity, QC/input-quality fields, `forecast_status`, `forecast_version`, `publication_state` (`unpublished | selected | replaced | withdrawn`), `selection_version`, and publication timestamp. Review responses also expose Plan 340 `capture_status`, `effective_preservation_status`, attestation ID, remaining reasons and the typed `preservation_at_publish` state (`verified | backup_pending` for a published decision); detail includes actor/time/reason decision history. `replaced` is historical publication, not withdrawal; its values remain available until reasoned retraction. If one eligible forecast ID is selected again after replacement, by-ID detail shows its latest decision while history preserves each decision ID separately. Preserve pagination totals after publication and tenant/station filtering. Choose non-conflicting route ordering before implementation. The change feed must use a transactionally allocated, commit-ordered publication sequence as its cursor rather than timestamp alone; serialized sequence allocation makes a later-committing event sort after already visible events. Return an opaque next cursor and bounded pages in sequence order, including replacement links and withdrawal tombstones. A client that retries a page or resumes after a same-time concurrent publication must neither lose nor invent an event. Document exact JSON in `docs/spec/types-and-protocols.md` and generated OpenAPI during implementation.

The implemented T1 integration contract is CHWRR OIDC access tokens; the actual provider is not yet known. `api/human_auth.py` validates configured issuer, audience, signature/JWKS, allowed algorithm, `iat`, `exp`, `nbf`, stable `sub`, MFA assurance, a maximum 30-minute token lifetime and bounded clock skew. A real IdP that cannot supply this contract needs an explicit reviewed security-policy change before activation. `(issuer, sub)` resolves to one local user UUID, active status, tenant and station-scoped `review`/`publish` grants; the operator grant/revoke CLI already exists. T2 writes the human UUID to `audit_log.actor_id` (`actor_type=user`), never token bytes. IdP endpoint, claims, JWKS rollover, MFA assurance mechanism and dashboard origin remain deployment inputs. No service token, including Plan 401's reviewer token held server-side by a dashboard, may call a review-candidate or write route; those requests must carry the named human's verified principal. T1's exact-origin `ScopedCorsMiddleware` already permits only GET/POST on `/api/v1/review/forecasts` for the configured human dashboard origin; keep that boundary for T3 and do not use wildcard credentialed origins.
